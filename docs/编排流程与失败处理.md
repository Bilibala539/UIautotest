# 编排流程与失败处理

> 本文是给**人读的**流程说明。Agent 执行层面的详细指令在 `.claude/agents/aw-orchestrator.md`。

---

## 一、正常流程（端到端）

```
用户需求
  │
  ▼
aw-orchestrator（总协调）
  │
  │  派发前：G1-G5 门禁检查（spawn codegen 前必须通过）
  │  ├─ G1: 目标页面已在知识库 → 否则先走 ①
  │  ├─ G2: 目标元素图片已注册 → 否则先走 ②
  │  ├─ G3: test 方法末尾有清理调用
  │  ├─ G4: 清理后能回到消息首页
  │  └─ G5: 同功能变体合并 parametrize（提示，不阻断）
  │
  │  派发前：MCP 批次空间认知查询（只注入相关页面，全量知识库不进子 Agent）
  │  ├─ get_related_pages("目标页面")
  │  ├─ get_navigation_path("起点", "目标页面")
  │  ├─ find_similar_tests("用例描述")
  │  └─ semantic_search("用例描述", source_type="docs")  ← 检索 runtime_experience.md
  │
  ├─① aw-explorer   摸清目标页面，输出 knowledge/draft/*.md
  │   调用方式：SendMessage（长驻，支持多轮对话）
  │   （验证后由 verify 转正到 pages/）
  │
  ├─② aw-element    截取目标 UI 元素，注册到 image_name_mapping.py
  │   调用方式：Agent()（子 Agent，每次干净上下文）
  │
  ├─③ aw-codegen    写业务 AW 方法 + PPUser 便捷方法 + pytest 用例
  │   调用方式：Agent()（子 Agent，每次干净上下文）
  │   prompt 包含：批次空间认知 + 相似用例 + 已知经验 + 任务描述
  │   （使用 vector_kb 查找相似用例和相关上下文）
  │
  └─④ aw-verify     跑 pytest，通过后：
      调用方式：Agent()（子 Agent，每次干净上下文）
      - image_ai/ 图片转正到 image/
      - draft/*.md 转正到 pages/（promote_knowledge.py）
      - 触发 auto_update.py 重建索引
```

**子 Agent 确认令牌**：aw-codegen/verify/element 被 spawn 后，必须先输出「阶段0完成：已读...」确认语，orchestrator 验证确认语存在后才读取结果；若无确认语则重新 spawn（最多 1 次重试）。

**经验沉淀**：每次子 Agent 返回 `[完成]` 后，orchestrator 将新发现的方法/限制追加到 `docs/runtime_experience.md`，供后续任务通过语义检索复用。

**串行约束**：① → ② → ③ → ④ 必须按序。同一批不相关页面的 ① ② 可并行，③ ④ 必须串行。

### 知识库自动更新

```
git commit（任何阶段）
    ↓ post-commit hook
auto_update.py
    ├─ 检测 pages/*.md 变更 → backlinks_generator.py（重建反向链接）
    └─ 检测知识/测试/文档变更 → embedding_pipeline.py --incremental（增量更新向量索引）
```

## 二、Git 存档点协议

每次进入 ③ codegen 阶段前，orchestrator 先建存档点：

```
派 codegen 前    →  git commit "checkpoint: pre-codegen [任务简述]"
verify 通过后    →  git commit "feat: [功能简述]"
verify 失败重试  →  git reset --hard HEAD（还原到 checkpoint）
超过 3 次失败    →  git reset --hard HEAD + 报告用户，停止重试
```

目的：codegen 写的内容可随时干净还原，不留脏数据。

## 三、失败回退路由

> 修复失败用例统一走 **fix-batch** 模式（`.claude/commands/fix-batch.md`）。
> 无论单个用例还是批量失败，都用同一套流程。

### Phase 0.5：共性根因分析（fix-batch 前置步骤）

修复失败用例时，fix-batch 在分派任何修复任务之前先做共性分析：

```
从每个失败 traceback 提取最后调用的 mumu.py 方法
  ↓
按方法分组（同方法 ≥2 个失败 = 疑似共性）
  ↓
二次验证（异常消息核心内容 + 栈帧行号 ±3 行，2 项一致才确认）
  ↓
交叉比对 PASS 用例（全 FAIL → 直接修方法；有 PASS → 对比调用差异）
  ↓
输出优先级队列：共性问题排前，独立问题排后
```

**AW 方法基线回归验证**：当修复涉及修改 `utils/aw/business/mumu.py` 时，自动触发基线回归——修复前后分别跑依赖该方法的测试文件，搞坏数 > 修好数则 revert，保护已有通过的用例。

每轮修复后重新执行 Phase 0 + Phase 0.5，不沿用上轮分析结论。

### 🔴 前置校验（Step 0，不可跳过）

修复任何失败用例前，先对比代码逻辑与文字用例：
- **一致**（代码意图对，实现有 bug）→ 正常修复
- **不一致**（代码偏离文字用例）→ 删除用例 → convert-cases 重新生成

### 修复分派

verify 跑完后，按失败类型回退到对应 agent：

| verify 报告的失败类型 | 回退到 | 原因 |
|---|---|---|
| `image_exists` 超时，图片质量差 | aw-element | 图不对，改代码没用 |
| OCR 找不到文字 | aw-element | 考虑改用截图断言 |
| AW 操作路径对不上知识库 | aw-codegen | 代码逻辑问题 |
| 设备异常 / ADB 断连 / 页面对不上 | aw-explorer | 重新核实页面路径 |
| conftest / fixture 报错 | 升级给用户 | 不是单个 agent 能修的 |

**最多回退 3 次**，仍失败则整理失败原因交给用户判断，不继续重试。

## 四、verify 失败时的排查顺序

verify 内部强制遵守以下顺序，避免图有问题反复改代码：

```
Step 1：再跑一次，确认是稳定失败还是偶发
  │
  ▼
Step 2：先看图片质量（image_exists 超时时）
  ├─ 含动态元素（角标/时间戳/头像）？
  ├─ 边缘留白过多？
  ├─ 截入窗口阴影？
  └─ 分辨率不是 540×960？
  │（图没问题再看代码）
  ▼
Step 3：看 AW 操作逻辑
  ├─ 步骤和探索记录是否一致？
  ├─ 前置操作是否到达目标页？
  └─ sleep 不够 / 有弹窗遮挡？
```

归因完成后，按第三节的表路由回退。

## 五、质量门控

### codegen 交付前（不可跳过）

1. 写代码前：明确方法的输入、动作、预期断言
2. 写代码前：列举失败路径，确认用例里每条都有对应断言
3. 写完后：实现是否覆盖了意图？用例是否覆盖了边界？
4. 交付标准：逻辑上确定能过，不是"应该没问题"

### verify 报告成功前（不可跳过）

- 必须贴 pytest 实际输出（passed/failed 行）
- 不允许"代码看起来对"就报完成

## 六、超时与卡住检测

orchestrator 派出任务后主动计时，各 agent 超时阈值：

| Agent | 超时阈值 |
|---|---|
| aw-explorer | 20 分钟 |
| aw-element | 15 分钟 |
| aw-codegen | 15 分钟 |
| aw-verify | 15 分钟 |

超时后：先发一条确认消息，5 分钟内无响应 → 标记失败，告知用户，不再静默等待。

---

## 七、codegen 自身失败（当前空白）

目前 orchestrator 只处理"verify 发现 codegen 写错"的情况。
若 codegen 在写代码阶段就自己报 `[失败]`（如：任务描述不清、找不到依赖），
orchestrator **尚无明确处理逻辑**——遇到此情况需人工介入。
