# 并行测试执行指南

> 本文档写给后续接手本项目的 AI 助手阅读。换机器后能快速理解并行机制，知道怎么跑、怎么修。

## 一句话原理

**预启动 N 个 MuMu 模拟器实例 → 测试文件均匀分片 → N 个独立 pytest 进程各管一个实例 → 汇总结果。**

不依赖 pytest-xdist（因为它每个 worker 进程各自调 `start_devices()` 会关掉旧实例重启，互相冲突）。

## 核心机制：INSTANCE_ID + SKIP_SESSION_LOGIN

两个环境变量控制整个并行逻辑：

| 变量 | 作用 | 设置位置 |
|---|---|---|
| `SKIP_SESSION_LOGIN=1` | 跳过模拟器启动和 APK 安装，直接复用已运行的实例 | `run_parallel.py` 子进程 |
| `INSTANCE_ID=N` | 指定当前 pytest 进程的设备索引 + 测试账号 | `run_parallel.py` 子进程 |

**设备端口是确定的**（`utils/devices.py:93-95`）：
```
instance_id=0 → port=16384 → serial=127.0.0.1:16384
instance_id=1 → port=16416 → serial=127.0.0.1:16416
instance_id=2 → port=16448 → serial=127.0.0.1:16448
```
公式：`port = 16384 + instance_id * 32`

**测试账号也是确定的**：每个实例绑定不同账号，避免同一账号多设备登录导致 session 互踢。
```
INSTANCE_ID=0 → userA (grp.popoqa67@corp.netease.com)
INSTANCE_ID=1 → userB (grp.popoqa73@corp.netease.com)
INSTANCE_ID=2 → userC (grp.popoqa74@corp.netease.com)
INSTANCE_ID=3 → userD (grp.popoqa75@corp.netease.com)
```
所有账号均在 test03 环境，密码相同。用例代码无需改动，仍写 `self.users("userA")`，框架自动按 INSTANCE_ID 映射到对应账号。

## 改动点说明

### conftest.py（2 处）

**1. 日志文件名加实例 ID（第 75-76 行）**
```python
_log_instance_id = os.environ.get("INSTANCE_ID", "0")
log_file = os.path.join(log_dir, f"test_{_log_timestamp}_inst{_log_instance_id}.html")
```
不加的话 3 个进程同一秒启动，`test_20260513_143022.html` 会碰撞。

**2. UsersFactory 支持 INSTANCE_ID + 账号映射（第 480-497 行 + 第 515-517 行）**

初始化时：
```python
instance_id = os.environ.get("INSTANCE_ID")
if instance_id is not None:
    self._instance_id = int(instance_id)
    self._device_index = self._instance_id
    # 每个实例绑定不同账号，instance 0→userA, 1→userB, 2→userC, 3→userD
    _ACCOUNT_KEYS = ["userA", "userB", "userC", "userD"]
    self._user_key_map = {"userA": _ACCOUNT_KEYS[self._instance_id]}
else:
    self._device_index = 0
    self._user_key_map = {}
```

`__call__` 开头重映射：
```python
if user_key in self._user_key_map:
    user_key = self._user_key_map[user_key]
```

串行模式（不设 INSTANCE_ID）行为不变：`_device_index` 默认 0，`_user_key_map` 为空，userA 就是 userA。
并行模式（INSTANCE_ID=1）时：`_device_index` 初始化为 1 → 绑定端口 16416；userA → userB → 用 grp.popoqa73 账号登录。

### run_parallel.py（新文件）

独立脚本，不依赖任何 agent。核心流程：

```
main()
 ├─ collect_tests()          ← 收集 test_*.py
 ├─ shard_tests()            ← 轮询分片（1,2,3 → 实例 0,1,2）
 ├─ start_devices(N)         ← 启动 N 个 MuMu，排列窗口，装 APK
 ├─ ThreadPoolExecutor       ← N 个线程
 │    └─ run_instance(i, shard[i])
 │         ├─ 设 SKIP_SESSION_LOGIN=1 + INSTANCE_ID=i
 │         └─ 执行 pytest <shard_files> -v --tb=short
 ├─ 实时输出每个实例的进度
 ├─ 汇总通过/失败/错误
 └─ 结果写入 parallel_results.json
```

## 用法

```bash
# 默认 3 实例跑全量 checklist
python run_parallel.py

# 2 实例跑前 10 个文件（验证用）
python run_parallel.py -n 2 -t 10
```

### 参数

| 参数 | 说明 | 默认值 |
|---|---|---|
| `-n, --instances` | MuMu 实例数 | 3 |
| `-t, --tests` | 限制测试文件数 | 全部 |

- **用例级日志**：`logs/{test_file}.html`，同一用例在不同实例上分别写，但由于例子文件名相同且我们不跨实例跑同一文件，不会冲突

## 换机器执行前必须检查

### 1. MuMu 安装路径

`utils/devices.py` 第 21 行：
```python
MUMU_INSTALL_PATH = r"C:\Program Files\Netease\MuMu\nx_main"
```
如果新机器安装了不同版本的 MuMu（如 MuMu 12 vs MuMu NX），路径和 exe 名可能不同。检查：
- `get_player_path()`（第 102-108 行）：查找 `MuMuPlayer.exe` 或 `MuMuNxMain.exe`
- 窗口名称在 `get_window_name()`（第 449-454 行）：`"MuMu模拟器12"` 或 `"MuMu模拟器12-{N}"`

### 2. ADB 路径

`utils/devices.py` 第 111-120 行，`get_adb()` 依次查找：
1. `{MUMU_INSTALL_PATH 的父目录}/vmonitor/bin/adb_server.exe`
2. `{MUMU_INSTALL_PATH}/adb.exe`
3. 系统 PATH 中的 `adb`

### 3. APK 下载地址

`utils/devices.py` 第 22 行：
```python
DOWNLOAD_URL = r"http://10.220.28.153/client_android/popo_origin-feature_workhub_9027_dev.apk"
```
这是内网地址，外网不可达。换机器后需更新为可用的 APK 地址。

### 4. MuMuManager 命令

`utils/devices.py` 中多处调 `MuMuManager.exe`（关闭实例、设置窗口大小等）。如果 MuMu 版本不同，命令行参数可能变化。

### 5. 系统资源

3 个 MuMu 实例并行需要：
- 每实例 ~2GB 内存 = 共 ~6GB
- CPU 核心：每实例 2 核（可在 MuMu 设置里调整）
- 磁盘 I/O：3 个模拟器同时读写可能成为瓶颈

## 故障排查

### 多个实例都没有启动成功

```
0/3 个实例就绪
```
- 检查 MuMu 是否已安装
- 手动运行 `MuMuPlayer.exe -v 0` 看能否单独启动
- 查看 `MUMU_INSTALL_PATH` 是否正确

### 某个实例报告端口连接失败

```
[FAIL] 127.0.0.1:16416 连接失败
```
- 手动执行 `adb connect 127.0.0.1:16416` 看返回
- `adb devices` 列出已连接设备确认
- 可能是 MuMu 崩溃或端口被占用，重启该实例

### 两个实例日志互相覆盖

说明 `conftest.py` 里 `INSTANCE_ID` 没有正确读到。检查：
- `run_parallel.py` 里 `env["INSTANCE_ID"]` 是否被正确传给子进程
- `conftest.py` 里 `os.environ.get("INSTANCE_ID", "0")` 是否正确

### 用例失败但串行模式能过

常见原因：
- **窗口焦点竞争**：虽然默认用 ADB 模式不需要窗口焦点，但如果有测试依赖 pyautogui 模式（如设置了 `FORCE_PYAUTOGUI_MODE=1`），多实例同时在桌面操作时互相干扰
- **资源争抢**：3 个实例同时读写磁盘，截图或日志偶尔失败
- **ADB 端口冲突**：`adb connect` 到 3 个端口时应看到 3 个独立设备。`adb devices` 确认每个端口都有 `device` 状态

### 扩展实例数

目前 `MAX_DEVICES = 3`（`utils/devices.py:26`）。如果要增加到 4+：
1. 改 `MAX_DEVICES = 4`
2. 确认端口计算正确（16384 + 3*32 = 16480 没有冲突）
3. 确认系统资源足够
4. 确认屏幕宽度能放下 4 个 540px 宽的窗口（需要至少 2160px，即 4K 显示器或虚拟桌面）

## 为什么不直接用 pytest-xdist

xdist 的 `-n N` 会启动 N 个 worker 进程，每个 worker 都是独立的 Python 进程。但本项目的 `start_devices()` 函数在启动前会**先关闭所有已有 MuMu 实例**（`utils/devices.py:471-474`）。如果 N 个 worker 进程几乎同时开始，它们会：

1. Worker A 启动 → 关掉所有 MuMu → 启动 N 个
2. Worker B 启动 → 关掉 Worker A 刚启动的 MuMu → 重新启动 N 个
3. ...

结果就是死循环。所以我们选择预启动 + 独立子进程的方案。
