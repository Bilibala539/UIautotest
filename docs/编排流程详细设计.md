# 编排流程详细设计

> 本文档描述 UIAutotest 团队当前**实际运行**的编排体系。
> 核心实现位于 `.claude/agents/aw-orchestrator.md`，本文是面向人的可读版本。

---

## 一、架构总览

```
用户需求（一句话 / 文字用例 / Excel）
  │
  ▼
┌────────────────────────────────────────────────────────┐
│                  orchestrator（主会话）                  │
│                                                        │
│  职责：拆解意图 → 路由模式 → 派发子 agent → 汇总交付   │
│  工具：Agent / SendMessage / TaskCreate / MCP 知识库    │
│  模型：opus                                            │
└───┬─────────┬─────────┬─────────┬─────────┬───────────┘
    │         │         │         │         │
    ▼         ▼         ▼         ▼         ▼
┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────────┐
│explorer│ │element│ │codegen│ │verify │ │spec-keeper│
│(sonnet)│ │(sonnet)│ │(haiku)│ │(sonnet)│ │(sonnet)   │
│探索App │ │截元素  │ │写代码  │ │跑验证  │ │管规范     │
└───────┘ └───────┘ └───────┘ └───────┘ └───────────┘
```

**关键原则**：orchestrator 不写代码、不操作模拟器，只做分派和汇总。

### 派发方式区分

orchestrator 有两种派发机制，按 agent 特性选择：

| 派发方式 | 适用 agent | 特点 |
|---------|-----------|------|
| **SendMessage（长驻 agent）** | explorer、spec-keeper | 双向通信，支持中途问答、多轮交互 |
| **Agent()（一次性子 agent）** | element、codegen、verify | spawn 一次执行，返回结果即销毁，不保留上下文 |

```python
# 长驻 agent：可来回对话
SendMessage(to="aw-explorer", message="探索消息设置页...")
# explorer 可以中途发回"这个页面有两个入口，走哪个？"

# 一次性子 agent：prompt 自包含，一次交付
Agent(subagent_type="aw-codegen", prompt="任务：... 完成标准：...")
# codegen 返回 [完成] 或 [失败]，对话结束
```

**选择依据**：需要中途决策/探索性质的用长驻，任务明确/产出确定的用一次性。

## 二、三种编排模式

orchestrator 收到需求后，按关键词匹配选择模式：

| 模式 | 触发关键词 | 产出 |
|------|-----------|------|
| convert-cases | "写用例""转自动化""覆盖XX功能" | pytest 可执行脚本 |
| enrich-kb | "探索""补充知识""更新页面" | 知识库 pages/*.md 更新 |
| fix-batch | "失败""修复""fix""红了" | 修复后的通过用例 |

无法判断时问用户确认。

## 三、模式一：convert-cases（核心流水线）

文字用例 → 可执行 pytest 自动化脚本的完整流程。

### 流水线

```
Step 1: 知识库预检
  orchestrator 查 MCP 知识库，确认目标页面是否已探索
  ├─ 已有 → 跳过 Step 2
  └─ 缺失 → 进 Step 2

Step 2: aw-explorer 确认页面路径
  输入：目标功能描述
  产出：pages/*.md + app_map.json 更新
  ⚠️ 仅在知识库缺页面时触发

Step 3: aw-element 定位/截取元素
  输入：元素清单 + 当前页面截图
  方式：ShowUI-2B 自动定位 → 精修 bbox → 裁剪 → 质量校验
  产出：image_ai/*.png + image_name_mapping.py 新常量
  ⚠️ 已有元素可跳过
  ⚠️ ShowUI 服务未运行时自动拉起（首次约 90s）

Step 4: aw-codegen 生成代码
  输入：结构化用例 + 页面知识 + 元素常量
  产出：AW 方法(mumu.py) + PPUser方法(user.py) + pytest 用例(tests/add_new/)
  ⚠️ 派发前必须通过 G1-G5 门禁检查

Step 5: aw-verify 验证
  输入：codegen 产出的文件列表
  产出：pytest 运行报告 + 图片转正(image_ai → image)
```

### 并行策略

- Step 2 + Step 3：不同页面/元素可并行
- Step 4 + Step 5：必须串行（代码写完才能跑）

### Git 协议

```
Step 4 前: git add -A && git commit -m "checkpoint: pre-codegen [任务简述]"
Step 5 通过: git add -A && git commit -m "feat: [功能简述]"
Step 5 失败: git reset --hard HEAD → 重新派 codegen（附失败原因）
超过 3 次: git reset --hard HEAD → 报告用户，等待人工判断
```

## 四、派发前门禁（G1-G5）

spawn aw-codegen 前 orchestrator 逐项检查：

| # | 检查项 | 验证方式 | 不过后果 |
|---|--------|---------|---------|
| G1 | 页面已在知识库 | `list_pages()` 有目标 page_id | 先派 explorer |
| G2 | 元素图片已注册 | grep image_name_mapping.py | 先派 element |
| G3 | 用例末尾有清理逻辑 | 任务描述含清理步骤 | 补充后再派 |
| G4 | 清理后回首页 | 任务描述末尾有回首页 | 补充后再派 |
| G5 | 一个 py 文件一个 test 方法 | 检查是否有多个 test 方法或 parametrize | ⚠️ 拆分；描述相似的用例可合为一个脚本，但仍只一个 test 方法执行一次 |

## 五、知识注入（派发子 agent 前）

orchestrator 用 MCP 查询本次任务相关上下文，注入子 agent prompt：

```
related_pages  = get_related_pages("目标 page_id")
nav_path       = get_navigation_path("消息列表页", "目标页面")
similar_tests  = find_similar_tests("当前用例功能描述")
experience     = semantic_search("功能描述", source_type="docs")
```

子 agent prompt 结构：
```
## 批次空间认知
{related_pages + nav_path}

## 相似用例参考
{similar_tests}

## 已知经验
{experience}

## 任务
{具体任务描述}
```

全量知识库不进子 agent，只注入相关片段。

## 六、ShowUI 元素定位集成

aw-element 的元素坐标定位使用 ShowUI-2B 多模态模型自动完成：

```
截图 + "元素描述"
  │
  ▼
ShowUI-2B 推理（~90s on GTX 1660 Ti）
  │
  ▼
返回 center + bbox
  │
  ▼
精修 bbox（紧贴 + 去角标 + 去阴影）→ 裁剪 → 质量校验
```

**服务模式**：
- 常驻 HTTP 服务 `127.0.0.1:7860`，模型加载一次
- locate/ground 命令自动检测服务：有就走 HTTP，没有就自动拉起
- 首次启动加载约 90 秒，之后每次推理约 90 秒

**调用方式**：
```bash
.venv-showui\Scripts\python.exe utils/showui_agent.py locate <截图> "搜索按钮"
# → {"status":"ok", "center":[469,57], "bbox":[439,27,499,87], ...}
```

## 七、失败回退策略

verify 报告失败时，orchestrator 按错误类型回退：

| 失败类型 | 回退目标 | 说明 |
|---------|---------|------|
| 图片匹配失败 | aw-element | 重新截图 |
| AW 逻辑错误 | aw-codegen | 重写代码 |
| 页面/设备对不上 | aw-explorer | 重新探索 |

最多回退 3 次，仍失败则整理诊断交回用户。

## 八、模式二：enrich-kb（丰富知识库）

不涉及编写自动化用例，只补充/更新应用知识。

四个子模式：

| 子模式 | 触发 | 流程 |
|--------|------|------|
| new-page | 知识库没有的页面 | explorer 探索 → 审核 draft → 转正 pages/ |
| update-page | "XX变了""改版了" | explorer 对比验证 → 覆写 pages/ → 检查级联 |
| add-feature | 跨页面功能记录 | 多页面探索 → 整合 digest/features/ |
| audit-kb | "巡检""检查准确性" | verify 逐页验证可达性 → 汇总报告 |

---

## 九、模式三：fix-batch（批量修复）

已有用例失败的诊断和修复流程。

```
Phase 0: 失败聚类分析
  读取所有失败 → 按根因分组 → 排优先级

Phase 1: 逐个处理
  Step 0: 代码-用例一致性校验
    ├─ 一致 → 正常修复
    └─ 不一致 → 删除 → convert-cases 重新生成
  Step 1: verify 诊断根因
  Step 2: 按根因派修复 agent
  Step 3: verify 重跑验证（最多 3 轮）
  Step 4: 修公共方法后跑同组其他用例
```

## 十、子 agent 通信协议

### 派发格式（orchestrator → 子 agent）

```
任务：<动词开头一句话>
目标功能：<功能点描述>
相关上下文：<知识注入片段>
完成标准：<什么算完成>
```

### 回报格式（子 agent → orchestrator）

```
[完成] 或 [失败]
文件变更：
  - <路径>（<描述>）
新增图片常量：<列表> 或 无
建议 verify 命令：pytest <路径> -v
遗留问题：<内容> 或 无
```

### 进度输出（子 agent 关键节点）

| 节点 | 格式 |
|------|------|
| 自检通过 | `[进度] 自检通过，开始写代码` |
| 遇到阻塞 | `[阻塞] <描述>，需要 orchestrator 决策` |
| 自检失败 | `[自检失败] <原因>` |

## 十一、双层知识库同步

任何知识库变更后必须同时更新 Graph 层和 Embedding 层：

| 触发事件 | 动作 |
|---------|------|
| explorer 探索完成 | app_map.json + pages/*.md + 图片常量索引 |
| element 截图完成 | mapping 注册 + app_map elements 补图片引用 |
| verify 转正图片 | mapping test_path→path + app_map 标记 verified |
| 任何 pages/*.md 变更 | `embedding_pipeline.py --incremental` + `backlinks_generator.py` |
