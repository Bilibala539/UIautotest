# AI 任务页与平台登录设计（"任务派发"模块）

> 2026-09-29 v1.0，产品设计师产出。依据 `docs/平台UI设计规范.md`（下称"规范"，基于 worktree 0874e79 版增补，与 uiautotest-dev 2026-09-29 版核对一致）。
> 范围：平台级登录（账号/会话/角色）+ "任务派发"页签的页面与交互设计。后端架构（server.py 加 API + 独立 dispatch_worker 进程 + .167/.176 小领导执行）已拍板，不在本稿范围；本稿给出前端消费的接口形状与建表字段建议。
> 本模块设计已回写规范：新增 5.6（登录与会话）、6.10（AI 任务逐页签清单）、2.2 状态表扩行、2.3 风险三档。

## 一、命名与定位

- **页签定稿："AI 任务"**（`data-page="tasks"`，页面 id `page-tasks`，新代码 CSS/JS 前缀 `tk-`），nav 插在**首位**（执行会话之前）。
- 命名理由：
  - 与现有页签命名语言一致（执行会话/包管理/测试套件——对象名词直给）。"任务派发"是动宾结构，混进名词序列突兀，且"派发"是平台视角的动作，用户视角里它是"我交给 AI 的任务"；
  - "AI 任务"与流水线"最近执行"的任务明确区分——两边都叫"任务"会混淆，"AI"前缀是事实陈述（执行者是大领导/小领导 agent），不是营销修饰，不犯"智能调度"式文案红线；
  - 页面内文案统一用"任务"（提交任务/任务列表/任务详情），不反复堆"AI"。
- 定位：**提交 → 跟踪 → 看报告**的任务工作台。不是运维调度台（不画拓扑、不做实时日志直播），不是项目管理（不做看板/甘特）。核心循环：提交 → AI 分析 → （审批/答疑）→ 执行 → 报告归档。

## 二、平台登录

### 2.1 方案裁定：page.html 内登录视图，不做独立 login.html

- `body.pre-auth` 状态下隐藏 `header` 与全部 `section.page`，仅渲染 `#page-login`；登录成功移除类名，恢复正常骨架。理由：单文件多页签是既定架构，token/字体/组件全在同一文件，独立 login.html 要复制一份样式基线，两处维护不值。
- **服务端是真闸门**：除 `/api/auth/*` 外全部 API 未登录返回 401 `{"error":"未登录"}`；管理员接口无权限返回 403。前端显隐只是体验层，逐请求鉴权在服务端。
- 前端加载顺序：页面初始化先调 `GET /api/auth/me`——401 则挂 `pre-auth` 且不发起任何页签数据加载；200 则正常初始化。会话中途过期：任意请求遇 401 统一转登录视图 + toast"登录已过期，请重新登录"（新代码统一走 `fetchJson()` 包装函数判定状态码；存量 fetch 不强改，P1 逐步收拢）。

```

                ┌────────────────────────────┐
                │  Swan 测试平台              │  ← 23px/700 --ink(页标题档)
                │  账号由管理员分配            │  ← 12px muted
                │                            │

                │  [______________________]  │
                │  密码                       │
                │  [______________________]  │
                │  [          登录         ]  │  ← Primary,全宽
                │                            │
                │  用户名或密码不正确          │  ← .field-error,仅失败时出现
                └────────────────────────────┘
        卡宽 min(400px,92vw),水平居中,margin-top 16vh,--card 白卡圆角 12px
```

- 输入框/按钮全站默认样式（白底 --line 边 8px 圆角），登录失败错误文案写进表单下方 `.field-error`（12px `--bad`），**统一文案"用户名或密码不正确"**，不区分"用户不存在/密码错误"（不给枚举账号的人喂信息）。
- 提交期间登录按钮 disabled + opacity .5（防重复提交，规范 4.7）；回车键等同点登录。
- **明确不做**：插画、渐变、"记住我"、验证码、找回密码链接。空态是路标不是海报——"账号由管理员分配"一句已回答"我没有账号怎么办"。

### 2.3 会话与账号机制（给后端的边界）

| 项 | 口径 |
|---|---|
| 会话载体 | HttpOnly + SameSite=Lax cookie；服务端 session 表或等价物 |
| 有效期 | 固定 7 天，到期 401 重登；不做滑动续期（内网工具，简单优先） |
| 密码存储 | 散列（PBKDF2/bcrypt 任一），明文不落库不进日志 |
| 初始账号 | 部署侧命令行/环境变量创建首个管理员（凭据进 .env.local，不进 git）；**页面不做自助注册、不做找回密码** |
| 登录失败限速 | P1：连续 5 次失败锁 1 分钟（后端计数即可，前端只如实展示错误） |
| 改密 | P0 管理员可改任何人密码；本人改密 P1 |

### 2.4 顶栏用户区（登录后常驻）

```
┌────────────────────────────────────────────────────────────────┐
│ Swan 测试平台                [账号管理]   zhangsan · 管理员   退出 │ ← h1 行 flex 两端
│ ──────────────────────────────────────────────────────────────  │
│ AI 任务 | 执行会话 | 包管理 | 流水线 | 测试套件 | 用例管理 | …      │
└────────────────────────────────────────────────────────────────┘
```

- 现有 `header` 的 h1 行外套 `.hdr-top`（`display:flex; justify-content:space-between; align-items:flex-start;`），h1 左、用户区右。
- 用户区元素（13px）：用户名·角色（`rgba(255,255,255,.85)` 纯文字）+ ghost 小按钮"账号管理"（**仅管理员渲染**）+ ghost 小按钮"退出"。
- 深色 header 上的 ghost 变体 `.hdr-user button`：透明底、`1px solid rgba(255,255,255,.35)` 边、白字；hover 底 `rgba(255,255,255,.12)`。不用品牌蓝（深底上蓝按钮是"AI 味"重灾区）。
- 退出 = `POST /api/auth/logout` → 回登录视图，无需确认（非破坏性）。
- 角色变更/停用即时生效（服务端逐请求校验）；被停用用户的下一次请求 401 转登录。

### 2.5 角色权限矩阵

| 能力 | 管理员 | 普通用户 |
|---|---|---|
| 登录/提交任务 | ✓ | ✓ |
| 任务可见范围 | 全部人 | 仅自己提交的（服务端强制过滤，不信任前端参数） |
| 审批（批准/驳回） | ✓ | ✗（接口 403，UI 不渲染按钮） |
| 答复疑问 | 仅自己的任务（P1 放开代答） | 仅自己的任务 |
| 冲突处理（重试/放弃合并） | 仅自己的任务 | 仅自己的任务 |
| 按人用量报表 | ✓ | ✗（自己的 token 合计在统计卡可见） |
| 账号管理弹窗 | ✓ | ✗ |

### 2.6 账号管理弹窗（管理员，`#acc-modal`）

结构对齐"功能模块管理"弹窗先例（modal 内表格 + 底部新建行）：

```
┌ 账号管理 ────────────────────────────────────────[关闭]┐
│ 建号后用初始密码登录;停用立即生效,数据保留              │ ← meta 13px muted
│ ┌────────┬──────────┬──────┬──────────┬─────────────┐ │
│ │ 用户名  │ 角色      │ 状态 │ 建号时间  │ 操作         │ │
│ │ admin  │ 管理员    │ 启用 │ 09-29    │ 改密          │ │
│ │ lisi   │ 普通用户  │ 启用 │ 09-29    │ 改密  停用    │ │
│ │ wang   │ 普通用户  │ 停用 │ 09-29    │ 改密  启用    │ │
│ └────────┴──────────┴──────┴──────────┴─────────────┘ │
│ 新建: [用户名] [初始密码] [角色▾] [添加](Primary)       │
│ 自己不能停用自己、不能改自己的角色;至少保留一个启用的管理员│ ← hint
└────────────────────────────────────────────────────────┘

```

- 新建：用户名（唯一，重复 409 提示"用户名已存在"）+ 初始密码（最短 6 位，内网工具不做复杂度强制）+ 角色 select（普通用户/管理员）→ toast"已创建用户 lisi"。
- 改密：420px 二级弹窗（`#acc-pw-modal`，新密码输入 + Primary 确认），**不做行内编辑**（规范 5.3）。
- 停用/启用：走 `confirmAction` 确认（停用文案写后果："停用后 lisi 将立即无法登录，已登录会话一并失效"）；自己这一行的停用按钮 disabled + title 说明。
- **不做删除账号**（历史任务/用量还挂在用户名上，停用已覆盖"人走了"的场景，删除只制造孤儿数据）。

## 三、任务生命周期与状态机

### 3.1 状态枚举与徽标配色（全部走规范 2.2，零新色）

| 状态 | 枚举值 | 徽标文案 | 色系 | 语义 |
|---|---|---|---|---|
| 待分析 | `pending_analysis` | 待分析 | warn 族 | 等大领导分析 |
| 待审批 | `pending_approval` | 待审批 | warn 族 | 等管理员拍板 |
| 疑问待答 | `questioning` | 疑问待答 | warn 族 | 等提交人答复 |
| 执行中 | `running` | 执行中 | brand（复用 `.running`） | AI 干活中 |
| 待处理冲突 | `conflict` | 待处理冲突 | warn 族 | 合并冲突，等提交人处理 |
| 完成 | `done` | 完成 | good（复用 `.passed`） | 终态 |
| 失败 | `failed` | 失败 | bad（复用 `.failed`） | 终态 |
| 已驳回 | `rejected` | 已驳回 | muted（复用 `.cancelled`） | 终态 |
| 已取消 | `cancelled` | 已取消 | muted（复用 `.cancelled`） | 终态（P1 撤回用） |

- **裁定**：四个"等人工/流程卡点"态共用 warn 族，徽标文字区分——规范 2.2 里 warn 族语义本就是「非正常推进的中间态」（skipped/env_blocked/cancelling 同族），本模块把它收敛为一句话：**黄=等人，蓝=在跑，绿=成了，红=砸了，灰=关了**。管理员找"待审批"、用户找"疑问待答"靠状态胶囊筛选与徽标文字定位，不靠发明新色。
- 完成/失败直接复用 `.passed`/`.failed` 类——与执行会话的结果视觉完全同形，全站"结果绿/红"一致（理念 1）。
- 新增 CSS 仅 4 个类，全部 token 配色：`.st-analyze/.st-approval/.st-question/.st-conflict { color:var(--warn); background:var(--warn-weak); }`（`.st-rejected/.st-cancelled` 直接用现有 `.cancelled`）。

### 3.2 状态流转表

| 当前态 | 事件 | 次态 | 触发者 |
|---|---|---|---|
| 待分析 | 分析完成（低/中风险） | 执行中 | 大领导 |
| 待分析 | 分析完成（高风险） | 待审批 | 大领导 |
| 待分析 | 提出疑问 | 疑问待答（记录挂起前阶段=待分析） | 大领导 |
| 待审批 | 批准 | 执行中 | 管理员 |
| 待审批 | 驳回 | **已驳回**（终态） | 管理员 |
| 疑问待答 | 提交答复 | 回到挂起前阶段（待分析/执行中） | 提交人 |
| 执行中 | 执行成功（非代码类） | **完成** | 大领导 |
| 执行中 | 执行成功（代码类，自动合并成功） | **完成**（merge_status=已合并） | 大领导 |
| 执行中 | 执行成功（代码类，合并冲突） | 待处理冲突 | 大领导 |
| 执行中 | 执行失败 | **失败**（终态，记失败原因） | 大领导 |
| 执行中 | 提出疑问 | 疑问待答（记录挂起前阶段=执行中） | 大领导 |
| 待处理冲突 | 重试合并 | 执行中 | 提交人 |
| 待处理冲突 | 放弃合并 | **失败**（终态，merge_status=已放弃，失败原因注明） | 提交人 |
| 待分析 / 待审批 | 撤回（P1） | **已取消**（终态） | 提交人 |

```
提交 ─► 待分析 ──低/中风险──► 执行中 ──成功──► 完成
           │                     │  │
           ├─高风险─► 待审批 ─批准─┘  ├─失败──► 失败(终态)
           │            │            ├─合并冲突─► 待处理冲突 ─重试─► 执行中
           │           驳回                     └──────放弃──► 失败(未合并)
           │            ▼
           │          已驳回(终态)
           └─疑问─► 疑问待答 ─答复─► 回原阶段(待分析/执行中均可发生)
```

- 疑问可多轮：答复后再次提问则再次进入疑问待答，问答历史全保留。
- 终态只有 完成/失败/已驳回/已取消 四个；"放弃合并"归入失败（报告保留，失败原因写明"合并冲突未解决，提交人放弃"），不新增第五个终态。

### 3.3 分析结论枚举（大领导产出，页面只展示）

- **任务类型**（纯分类，中性 chip）：代码修改 / 测试执行 / 问题排查 / 环境维护 / 其他。
- **风险等级**（severity 型，规范 2.3 风险三档）：高风险（`--bad`/`--bad-weak`）→ 走审批闸门；中风险（warn 族）；低风险（中性）。
- **目标机**：167 平台机 / 176 构建机（显示名与机器监控页一致；分析前为 `-`）。

- **列定义（7 列，管理员多"提交人"共 7；普通用户无提交人列 6 列）**：任务 / 状态 / 目标机 / 提交人(仅管理员) / token / 提交时间 / 操作。
- **任务列**：第一行标题（可点行整体开抽屉，不放"查看"按钮）；第二行 `.cd-case-title` 风格次行——任务号（等宽 12px muted）· 类型（中性 chip）· 风险（三档 chip）。类型/风险是分析后才有的属性，次行承载正好，不单开列（控制列数 ≤7±2）。
- **筛选胶囊**（复用 `.cd-pills`）：
  - 全部＝不过滤；
  - 进行中＝待分析+待审批+疑问待答+执行中+待处理冲突；
  - **需我处理**＝角色相关：管理员→待审批；普通用户→疑问待答+待处理冲突。这是本页最高频的过滤动作（管理员开页先看闸门，用户开页先看"AI 在等我"），胶囊里给足入口；
  - 已结束＝完成+失败+已驳回+已取消。
- 搜索 300ms 防抖，匹配标题/任务号；有激活筛选时"重置"描边变 `--brand`（规范 5.2）。
- 默认排序：提交时间倒序；**需我处理**选中时同为时间倒序（不搞置顶魔法，筛选已经够定位）。
- token 列：`num` 右对齐 tabular-nums 千分位；分析前 `-`。
- 提交时间列：相对时间 + title 绝对时间（规范 5.4）。
- **操作列**（固定最右，pinLast）：仅"待审批"且管理员渲染两个小 ghost 按钮「批准」「驳回」（5px 10px / 12px 次要档）——批准点开确认弹窗（cfm-modal，确认按钮品牌色变体），驳回点开驳回弹窗；按钮 `stopPropagation` 防触发行点击。其余状态操作列 `-`（详情走行点击，不作行内编辑）。
- 分页沿用 `.cd-pager`。

### 6.2 疑问闭环交互

- 疑问卡 `warn-weak` 底 10px 圆角，问答对上下排列（问/答前缀 + 人 + 相对时间）；多轮按时间正序。
- 疑问待答态：答案输入框 + Primary「提交答复」；答复成功 toast"已答复，任务继续执行" + 状态徽标回到挂起前阶段。
- 仅提交人（本人）可答复；管理员视角只读（P1 放开代答）。
- 问答历史**完成后仍保留**——报告里没写清的事，问答是第一手上下文。

### 6.3 审批闸门交互

- 管理员在抽屉内：**批准** = Primary，点开 `confirmAction` 确认（标题"批准执行任务 TASK-xxx？"，正文带分析结论摘要"类型 代码修改 · 风险 高风险：将修改 cases/driver/login 下 2 个 YAML……"——批之前最后看一眼要放出去干什么）；**驳回** = ghost，点开 `#tk-reject-modal`（420px，z-62 盖过抽屉：理由 textarea 可选 + ghost 取消 + 实底 `--bad` 确认驳回）——驳回必须给提交人一个说法，理由落库并在抽屉"审批"块旁持久展示。
- cfm-modal 确认按钮新增 `.brand` 变体（`--brand` 实底）用于"批准"这类**放行型**确认；`--bad` 实底仍只用于删除/驳回类破坏性确认。
- 提交人视角同区块只渲染一行灰字等待说明，不渲染按钮。

### 6.4 冲突处理交互（待处理冲突态）

- 抽屉内"产物"块显示 worktree 路径（复制按钮）与冲突说明（大领导写明冲突文件），提交人线下在自己环境解决后回来点：
  - 「我已解决，重试合并」= Primary → `confirmAction` 确认（"确认已解决冲突并重试合并？"）→ 状态回执行中；
  - 「放弃合并」= ghost → confirmAction（`--bad` 确认，后果文案"任务将以失败结束，已完成的修改保留在分支上"）→ 终态失败。
- 两个按钮仅提交人可见。

### 6.5 执行报告 Markdown 渲染（`.md-body`）

- **自写白名单渲染器，不引 marked/DOMPurify**（与"不引组件库"同口径；报告是 AI 产出，结构可预期，一个 ~120 行函数够用）。安全次序固定：**先整体 HTML-escape，再按白名单结构还原**——报告内容里的任何 `<script>` 都只能是文本。
- P0 白名单：`#`/`##`/`###` 标题、无序/有序列表、`**粗体**`、`` `行内代码` ``、``` 围栏代码块、`|` 表格、段落；链接只渲染 `http(s)://` 明文（`<a target="_blank" rel="noopener">`，`--brand` 色）。渲染不了的原样出文本，不报错。
- 排版（抽屉内）：正文 13px/1.6；标题 15px/600（不跳大字号）；代码块复用 `pre` 样式（单块 max-height 420px 内滚）；表格 3.2 紧凑档加 `--line` 边。
- 报告在任务终态才渲染；执行中显示灰字"任务执行中，报告完成后显示"。

### 6.6 产物与 token

- 分支名/worktree 路径：等宽 12px `--neutral-weak` 底 chip 式呈现（对齐 `#cdd-file-path` 先例）+「复制」小按钮（复制成功走 toast，规范 8.3 同款）。
- 合并状态四值：已合并（good 文字）/ 待合并（muted）/ 有冲突（warn 文字）/ 已放弃（muted）——复用现有 token，不加新色。
- token 行：`输入 x · 输出 y · 合计 z`，tabular-nums 千分位。

## 七、刷新与轮询

- P0：显式「刷新」按钮 + 切页签自动重拉（规范 5.5 基线）。
- **P0 附加（对齐 2026-09-28 对账轮询先例）**：本页签激活期间 15s 轻轮询（`TK_POLL_MS=15000`，`reconcileStart` 同款实现：`document.hidden` 即跳过、切走页签即停），重拉列表+统计卡+用量表。理由：提交后用户就停在列表上等状态走，AI 任务的状态变化以分钟计，15s 粒度刚好，且实现模式仓库里现成。
- 抽屉打开期间轮询**跳过抽屉重拉**（防止把用户正在输入的答复文本冲掉），抽屉内给 ghost「刷新」按钮手动更新。
- 不做 WebSocket、不做秒级轮询（规范"明确不做"清单 + 状态粒度不需要）。

## 九、API 形状（前端消费面；worker 内部通道由后端自定）

```
POST /api/auth/login                      {username,password} → 200 {username,role}+Set-Cookie | 401
POST /api/auth/logout                     → 200
GET  /api/auth/me                         → 200 {username,role} | 401
GET  /api/auth/users                      (admin) → {items:[{username,role,status,created_at}]}
POST /api/auth/users                      (admin) {username,password,role} → 201 | 409 已存在
POST /api/auth/users/{name}/password      (admin) {password} → 200
POST /api/auth/users/{name}/status        (admin) {status} → 200 | 400 自停/最后一个管理员
GET  /api/tasks?bucket=&status=&q=&submitter=&page=&pagesize=
                                          → {items:[…],total,page,pagesize}
                                          (普通用户服务端强制 submitter=self,忽略越权参数)
POST /api/tasks                           {title,description,desired_time?} → 201 {task_id}
GET  /api/tasks/{id}                      → 详情(含 questions[],events[],report_md,tokens,产物)
POST /api/tasks/{id}/answer               {answer} → 200（仅提交人,状态=疑问待答）
POST /api/tasks/{id}/approve              (admin) → 200
POST /api/tasks/{id}/reject               (admin) {reason} → 200
POST /api/tasks/{id}/merge-retry          (提交人,状态=待处理冲突) → 200
POST /api/tasks/{id}/merge-abandon        (提交人,状态=待处理冲突) → 200
GET  /api/tasks/usage                     (admin) → {items:[{username,submitted,running,done,failed,tokens_total}]}
```

- 列表 item 字段（前端渲染所需最小集）：`task_id,title,status,task_type,risk,target_machine,submitter,tokens_total,created_at`。merge_status/report 等只在详情返回。
- 统计卡/用量表可由列表接口附带（`stats` 字段）或独立接口，由后端定；前端只约定渲染。

## 十一、理念映射（规范 1.1 七条逐条）

- **理念 1 状态即颜色**：九态全走 2.2 表零新色；warn 族收敛为"等人"，done/failed 复用 `.passed/.failed` 与执行会话同形；风险三档属 severity 分类、有 P0-P3 先例。同页徽标不混用点/胶囊形态。
- **理念 2 密度服务扫描**：7 列内、类型/风险降任务列次行；token/时间 tabular-nums；无插画无渐变无多余卡片。
- **理念 3 渐进披露**：列表只留扫描层（标题+状态+机器+token+时间），问答/报告/产物/分析说明全在抽屉。
- **理念 4 展示与编辑分离**：列表只读；作答/审批/冲突处理都是抽屉里的显式动作块；行内"批准/驳回"是快捷入口且必过确认弹窗，不做无确认的行内写操作。
- **理念 5 每区块一个主动作**：工具栏 Primary=提交任务；提交弹窗 Primary=提交任务；抽屉疑问块 Primary=提交答复；审批块 Primary=批准（驳回 ghost 走弹窗）；冲突块 Primary=重试合并。各块不叠加。
- **理念 6 空态是路标**：列表空="还没有 AI 任务，点右上角'提交任务'把活派给 AI"；筛选无结果/加载失败三分文案；报告区执行中给预期文案。
- **理念 7 反馈轻量，异常可见**：全 toast；15s 轮询仅页签激活；驳回理由、失败原因、问答历史终态后全部保留可见（失败的数据也是数据）。

## 附：本模块自查清单（开发自测追加项）
