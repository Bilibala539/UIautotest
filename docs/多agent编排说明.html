UIAutotest 多 Agent 编排

整理自 CLAUDE.md 团队分工约定与 .claude/agents/ 六个蓝图 · 2026-09

简单说:项目里定义了六个 AI 角色,一个管调度,五个干具体的活。你说需求,调度者判断该走哪条流程,把活拆给对应角色,干完汇总给你。整个流转过程有存档、有检查点,出问题能回滚,不会越改越乱。

下面按"谁在干活 → 活怎么流转 → 怎么保证不出错"的顺序讲。

一、团队构成

flowchart TB USER["开发者"] ORCH["aw-orchestrator(主会话)
拆需求 / 派活 / 汇总"] EXP["aw-explorer
探索 App,维护知识库"] ELE["aw-element
截 UI 元素图,注册常量"] CODE["aw-codegen
写 AW 方法和 pytest 用例"] VERI["aw-verify
跑测试,归因失败,转正图片"] SPEC["spec-keeper
维护 openspec 文档"] USER --> ORCH ORCH --> EXP & ELE & CODE & VERI ORCH -.-> SPEC

两个值得注意的设计:

生命周期分两种。explorer 和 spec-keeper 是长驻的,通过消息双向通信——探索页面需要积累上下文,中途被打回来补充信息是常态,实例活着才方便。element、codegen、verify 则是每次任务新建、干完销毁,上下文干净,互不影响,同一批不相干的任务还能并行开好几个实例。

模型按任务难度分级。探索页面和调度派活最难,用 opus;截图裁剪是量大但规则明确的精细活,用 sonnet;按模板写代码、跑测试、维护文档,haiku 就够。这样整体成本能压下来。

角色模型产出
orchestratoropus不产出代码,产出拆解后的任务和最终交付物
exploreropus知识库文档 pages/*.md、页面地图 app_map.json
elementsonnet元素截图 image_ai/*.png + image_name_mapping.py 常量
codegenhaiku业务 AW 方法、tests/ 下的 pytest 文件
verifyhaiku测试报告、失败归因、图片转正
spec-keeperhaikuopenspec 提案和规范文档

二、三条流水线

orchestrator 收到需求后按关键词路由,判断不了就直接问你,不猜:

流水线你说什么会触发干什么
convert-cases"把这条用例转自动化"、"覆盖 XX 功能"文字用例 → 可执行的 pytest 脚本
enrich-kb"探索一下 XX 页面"、"知识库过时了"补充、更新、巡检知识库,不写代码
fix-batch"跑挂了"、"红了"、"修一下"诊断失败用例并修复

convert-cases:文字用例转自动化

flowchart LR A["文字用例"] --> B["spec-keeper
解析成结构化步骤"] B --> C["explorer
确认页面路径"] C --> D["element
截取/复用元素"] D --> E["git 存档点"] E --> F["codegen
生成代码"] F --> G["verify
跑测试"] G --> H["通过则 commit"]

其中探索和截图两步,如果知识库里已经有了会自动跳过,所以同一功能第二次跑会快很多。不同页面之间的探索和截图可以并行,但生成代码和跑测试必须串行——它们依赖上游产物。

enrich-kb:知识库维护

按场景分四个子模式:

  • new-page —— 探索新页面。explorer 先写草稿放到 draft/ 目录,经过"文档结构审核 + 实机走一遍确认可达"两道检查,才转正进 pages/。半成品不会污染正式知识库。
  • update-page —— 页面改版了。explorer 做对比验证,列出旧值到新值的变更;verify 按新路径实机复核;orchestrator 检查哪些页面引用了它、哪些图片常量过时了。
  • add-feature —— 记录跨页面功能的完整流程,为以后写用例铺路。
  • audit-kb —— 巡检。verify 逐页实机走一遍,出 ✅/⚠️/❌ 报告,顺手检查文档层和向量索引层是否一致,不一致的自动修复。

fix-batch:失败修复

flowchart TB A["失败输入
pytest 报告/日志"] --> B["聚类:按根因分组排优先级"] B --> C{"代码和原始用例描述一致吗"} C -- 不一致 --> D["删掉,回 convert-cases 重新生成"] C -- 一致 --> E["verify 诊断根因"] E --> F["图片问题 → element 重截图"] E --> G["代码问题 → codegen 修"] E --> H["路径问题 → explorer 查"] F & G & H --> I["verify 重跑,最多 3 轮"] I --> J["改了公共方法的话,重跑同组其他用例"]

先聚类再修,是因为批量失败往往同一个根因——比如页面改版导致某张元素图全部失效。修掉一个根因,一批用例跟着好,比逐条修快得多。另外动手前先校验代码意图和用例描述是否一致,免得在本来就写错的需求上浪费时间。

三、怎么保证不出错

多 agent 自主协作最大的风险是越改越错、静默失败。这套体系五层兜底:

  1. 派发前门禁(G1-G5)。codegen 开工前 orchestrator 逐项检查:页面在知识库里吗、元素图注册了吗、用例末尾有清理步骤吗、能回到首页吗、参数变体合并了吗。不满足就先补前置,不带病派活。
  2. 知识按需注入。spawn 子 agent 时用 MCP 检索,只把和本次任务相关的知识片段写进任务书,不喂全量库。子 agent 不用自己在几万行知识库里翻。
  3. Git checkpoint。每次派 codegen 前先 commit 一个存档点;verify 通过才 commit 正式成果;失败就 reset --hard 干净回滚,重新派发时附上具体失败原因。三次仍失败就停手报告,不会静默重试。
  4. 失败定向回退。verify 报"图片匹配失败"回 element,报"AW 逻辑错"回 codegen,报"路径走不通"回 explorer。最多回退三次,再不行整理清楚原因交给你判断。
  5. 超时检测。每个角色有超时阈值(element 15 分钟,codegen 15 分钟,explorer 20 分钟)。超时先问一次进度,五分钟没回音就标失败通知你,不无限等。

另外有个经验沉淀的闭环:子 agent 交付后,orchestrator 检查返回里有没有新发现(验证过的方法、踩过的坑),追加到 docs/runtime_experience.md,git 提交后 hook 自动重建向量索引。下次派任务时,相关经验会被检索出来注入任务书——同一个坑不踩第二次。

四、知识库:所有角色的共享记忆

agent 之间能对齐认知,靠的是同一份知识库,通过 MCP 暴露,分两层:

flowchart LR KB["explorer_output/knowledge/"] KG["Graph 层
页面怎么走,谁引用了谁"] VE["Embedding 层
语义搜索相似用例和经验"] AG["各 Agent"] KB --> KG & VE KG & VE --> AG

Graph 层回答结构性问题:"从消息列表怎么走到设置页?" Embedding 层回答语义问题:"和'发消息后撤回'相似的历史用例有哪些?" 写新用例前先查一遍,是所有角色的固定动作。

两层必须同步更新——这是硬规则。改了文档要重建向量索引,改了页面地图要同步文档,orchestrator 负责检查。

五、日常怎么用

cd E:\UIAutotest
claude

/bootstrap-team        # 拉起团队,幂等,重复执行安全

"帮我探索一下设置页面"          → 走 enrich-kb
"把这条用例转成自动化"          → 走 convert-cases
"昨晚挂了 20 个,修一下"        → 走 fix-batch
注意:/bootstrap-team 引用的 TeamCreate、TaskCreate 等工具在当前版本 Claude Code 已废弃,首次使用前需要把 bootstrap-team.md 和几个 agent 蓝图改写成 Agent + SendMessage 方案,是一次性的适配工作。

使用上不用记哪个角色干什么,直接描述需求,orchestrator 会路由。它来问你"这是修复还是新增用例"的时候,说明判断不了,直接答就行。
